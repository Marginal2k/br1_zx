# Чёрный Ворон: форматы ресурсов и инструменты (фаза 2b-assets)

Игра берёт ресурсы из `assets/` (двоичные файлы в том виде, как их делали утилиты автора, `INCBIN` в `src/`, упаковка в `build.py`).
Теперь для каждого семейства есть **редактируемая** форма в `assets_src/` (PNG, UTF-8 `.txt`, CSV) и пара конвертеров
«двоичный <-> редактируемый», проверенная побайтно. C++ утилиты автора (Borland C++, DOS) заменены модулями Python.

```
python tools/assets.py export [--assets assets] [--out assets_src]   # двоичные -> редактируемые (assets_src уже создан)
python tools/assets.py import [--src assets_src] [--out build/assets] # редактируемые -> ровно те двоичные, что нужны сборке
python tools/assets.py list                                            # какие группы во что превращаются
python tools/levels.py export | import                                 # доп. уровни 1999 г. (reference/lw2024) <-> assets_src/levels_ext
python tools/check_assets.py                                           # доказательство круга, код возврата 0 = всё совпало
```

Нужны Python 3 и Pillow. Модули: `tools/zxio.py` (ввод-вывод), `tools/gfx.py` (графика), `tools/text.py` (тексты), `tools/maps.py` (карты и герои),
`tools/levels.py` (блоки доп. уровней), `tools/assets.py` (разбиение на группы, командная строка), `tools/check_assets.py` (проверка).

это всегда 256x192 (32 байта в строке); конвертер забирает из него прямоугольники фиксированной формы.

## 2. Графика

### 2.1 Экраны Спектрума

* `.bin` 6144 байта и первые 6144 байта `.scr` - стандартная раскладка видеопамяти: адрес строки `y` = `((y&0xC0)<<5) | ((y&7)<<8) | ((y&0x38)<<2)`. Бит 7 - левая точка, 1 - чернила.
  PNG - 256x192, 2 цвета (чёрный - чернила).
* `.scr` 6912 байт = 6144 бит + 768 атрибутов (`ink | paper<<3 | bright<<6 | flash<<7`). PNG - цветной (индексы 0-7 обычные, 8-15 яркие; RGB `#D7` и `#FF`).
  **Рядом лежит `NAME.orig.scr`** - исходный файл: PNG не видит скрытого (какой цвет «чернила», какой «бумага» в однотонной ячейке; мигание; биты под одинаковым цветом).
  Импорт берёт из `orig.scr` каждую ячейку 8x8, чей вид в PNG не изменился, а изменённые кодирует заново (не более 2 цветов одной яркости в ячейке:
  бумага - более частый цвет, ярче - если есть яркие). Без `orig.scr` картинка получается **визуально та же**, но байты `.scr` отличаются (проверено, п. [4] `check_assets.py`).
  Не удаляйте `*.orig.scr`; правите PNG, а `orig.scr` пусть остаётся (устаревший не мешает).

### 2.2 Ландшафт `w1spr.dat ... w4spr.dat` (12288 байт = 384 тайла по 32 байта)

Тайл 16x16 хранится по столбцам: 2 столбца по 16 байт (сначала левый байт всех 16 строк, потом правый). Номера тайлов (WLAND.CPP, комментарий):
0 граница; 1-3 трава; 4-5 камни; 6 пни; 7/8 дорожка людей/кунгов; 9-16 тропы; 17-25 пепелище; 26-29 углы берега; 30-47 мосты; 48-50 -; 51 низ забора; 52-55 прямые берега;
56 вода (анимация); 57-60 берега (непроходимые, анимация); 61-63 лес; 64-72 забор; 78 шахта; 79 стройка 3x3; 80-85 строительство людей; 86-93 здания людей; 94-99 строительство кунгов;
100-107 здания кунгов; 108 строительство 2x2; 109 строительство избы; 110 изба; 111 строительство хибары; 112 хибара; 113-127 анимация воды;
**128-367 расширение зданий 3x3** (8 «хвостов» на каждое здание `n < 108`: `128 + (n-78)*8 + 0..7`), **368-382 расширение 2x2** (3 хвоста на здание `n >= 108`: `368 + (n-108)*3 + 0..2`), 383 невидимое поле.
Тайл здания записан как «центр» (номер `n`) и хвосты; на карте хвост хранится кодами 120..127 («направление к центру»).

Листы автора на один ландшафт (типы 1, 2, 4 - ландшафт «снаружи», 3 - подземелье): `wNcity` (здания людей), `wNbuild` (строительство и здания кунгов), `wNland` (сетка 16x12 тайлов 16x16);
у ландшафта 3 только `w3land`. Здания размещены по 48x48 точек (3x3 тайла), порядок и позиции взяты из массивов `l1s1, l1s2, l1s3, l2s1` (`tools/gfx.py`), оставшиеся тайлы заполняются `0x55`
(в данных таких нет: все 384 тайла заняты). Импорт пишет тайлы в тех же номерах.

Файлы PNG: `gfx/land/w1city.png, w1build.png, w1land.png, w2*..., w3land.png, w4*...` (256x192, чёрный = чернила).

### 2.3 Спрайты героев и разное (`wshum, wsorc, wscreat1, wscreat2, wmisc, wgrizold`)

Данные: пары байт `(M, M xor R)`, где `M` - маска (1 - точка принадлежит силуэту), `R` - рисунок (1 - чернила); идут блоками по столбцам (столбец байт, 16/24/32 строк).
Раскладки (число спрайтов, размер в байтах x строк на листе): `wshum, wsorc` - 192 блока (2x16 и 3x24) из `whum1+whum2` / `worc1+worc2`; `wscreat2` - 30 блоков 2x24 из `wcreat2` (строки 48-143);
`wscreat1` - 135 блоков из `wcreat1`, `wcreat2` (строки 0-47), `wmisc` (строки 80-103); `wmisc.dat` - 52 блока (2x16, 4x32, 1x8) из `wmisc` (строки 0-71); `wgrizold` - 16 блоков 2x16 из `wcreat1` (строки 144-159).
Точные позиции - в `tools/gfx.py` (`Rec`, класс повторяет циклы `WHERO.CPP`; блоки на листе не пересекаются, проверяется).

PNG - **4 цвета**: индекс = 2*маска + рисунок: белый (0,0) - вне силуэта (прозрачно); светло-голубой (маска 1, рисунок 0) - силуэт, бумага; **чёрный** (1,1) - силуэт, чернила;
красный (маска 0, рисунок 1) - «чернила вне силуэта», так быть не должно. Листы: `gfx/heroes/{whum1,whum2,worc1,worc2,wcreat1,wcreat2,wmisc}.png`. Участки листа вне блоков игнорируются.

### 2.4 Кнопки, панель, шрифт, имена (`WBAR_BUT.CPP`)

* `whumbutt.dat`, `worcbutt.dat`: 81 кнопка 24x23 (3 байта x 23 строки), по столбцам, **плюс один байт 0 в конце** (5590 = 81*69+1). Лист 256x216: 10 кнопок в ряду, ряд = 24 строки.
* `wbar.dat` (1536): панель управления, 8 байт x 192 строки (64x192), по столбцам, с байтового столбца 24 листа `wbar`.
* `wfont.fnt` (912): 114 глифов 8x8 по 8 байт; на листе с байтового столбца 18, 6 глифов в строке (48x152).
* `wnames.dat` (1932): 46 названий 48x7 (6 байт x 7 строк, по столбцам); на листе ячейки 6 байт x 8 строк (строка 0 ячейки не используется), 24 ячейки в колонке, 2 колонки (байтовые столбцы 0 и 6).
  Все три лежат на одном листе `gfx/panel/wbar.png` (256x192), как у автора (`wbar.tif`).

### 2.5 Заставка интро и ролики

* `intro/xlag_bl0.dat`, `xlag_bl1.dat` (12800): 5 кадров 160x128 (20 байт x 128 строк подряд, по строкам). PNG: `gfx/intro/xlag_bl?.png`, 5 кадров рядом (800x128).
* `intro/flick/wani?_0.bin`, `wani?_1.bin` (16128 = 8 кадров по 2016 = 14 байт x 144 строки, по строкам): 24 ролика (`2-9, a-j, u-z`). PNG на ролик: `gfx/flick/flick_?.png` 896x288, 8 кадров в строке:
  верхняя строка - кадры файла `_0`, нижняя - `_1`. (Порядок файлов на диске задаёт `build.FLICKS`.)
* `wnf1.fnt` (768), `wnf2.fnt` (96): шрифты инструкции, по 8 байт на глиф (96 и 12 глифов): `gfx/fonts/wnf1.png` (16 в ряду), `wnf2.png` (12 в ряду). Тот же формат, что `wfont.fnt` (`wfont.fnt` лежит в `wbar.png`).

## 3. Тексты

Текст в игре - номера глифов шрифта, а не ASCII. Ниже таблицы «номер -> символ» (из исходников автора). В `.txt` каждый глиф - один символ Unicode. **Латинские и кириллические буквы одинакового начертания - разные глифы**:
в основной таблице есть только латинские `N R S I F Y D J L G U a b c d e f g h` и кириллица; в таблице инструкции латинские `Z V N S D F G J L W Q R Y U I`, а `Е Т М А К Н О Р С Х В` - кириллические;
в готовом тексте автора встречаются смеси (`ТR-DОS`, `JАМ`, `SYМ`) - это не ошибка, так нарисованы глифы. Если символа нет в таблице, импорт останавливается с номером строки.
Номера глифов, которых кодировщик автора никогда не выбирает (повторы `^` и `+` в таблицах), пишутся как `{N}`.

Служебные коды: `127` - конец строки задания / блока / прокрутки; в инструкции `126` - конец строки, `127` (`=` в тексте) - служебный маркер конца раздела; `>=128` - пара из словаря `winstrcm.dat`.

### 3.1 `text/flick.txt` -> `data/wflictxt.bin` (7488 = 36 блоков по 208)

Формат файла - **тот же, что `WFLICTXT.TXT` автора** (в UTF-8, LF): блок - строки текста, затем строка `#` (или `$`; различие значения не имеет, 6 блоков, закрытых `$`, оставлены как у автора).
Блок = 16 строк по 13 глифов, хранится **по столбцам** (`buf[позиция 0..12][строка 0..15]`); пустые строки в конце блока можно не писать (добиваются пробелами). Строка центрируется:
смещение `(13 - длина)/2` (целочисленное). Строка не длиннее 13, блок не длиннее 16 строк. Если ряд в двоичных данных не получается центрированием, он записан как `|13 символов точно|`.
Рамки - буквы `a b c d e f g h` (уголки/линии): `abbbbbbbbbc`, `d  Текст e`, `fgggggggggh`.

### 3.2 `text/victory_human.txt`, `victory_orc.txt` -> `data/wvicthum.dat`, `wvictorc.dat`

Прокрутка титров победы: строки по 12 глифов подряд, центрирование `(13 - длина)/2`, кончается строкой `#` -> в файл дописывается байт 127. Строка длиннее 12 - ошибка.

### 3.3 `text/tasks.txt` -> `task/w000.tsk ... w216.tsk` (33 файла по 63 байта)

`[w101]`, затем три строки `|...|` ровно по 20 глифов (пробелы значимы), в файл: `20 глифов, 127, 20, 127, 20, 127`. `w000` - заставка демонстрации. Задания читает код уровня (`TASK_M` в `src/levels/w_???.asm`).

### 3.4 `text/instr.txt` -> `data/winstr.dat` (11567) + `winstrcm.dat` (256)

В `instr.txt` - развёрнутый текст инструкции (18005 глифов): строки как есть, `=` - служебный маркер. Игра хранит его сжатым (порт `WINSTR.CPP`, воспроизводит оба файла побайтно):
1. `*` -> пробел; пробел перед концом строки отбрасывается (один); конец строки (`CR LF`) -> 126; `=` -> 127; остальное - номер глифа по таблице инструкции (первое совпадение среди первых 111).
2. Считаются все пары соседних кодов `< 100`; 128 раз выбирается самая частая пара (при равенстве - первая по `(a, b)`), её счётчик гасится.
3. Слева направо пара из словаря заменяется кодом `128 + номер`. Словарь (128 пар по 2 байта) - `winstrcm.dat`, игра читает его при выводе текста.
Меняя текст, словарь и сжатие получаются заново автоматически (следите за размером: сейчас 11567 байт, игра держит `winstr.dat` рядом с кодом инструкции - см. `src/start1/w_instr.asm`).

## 4. Карты и герои уровней

`map/w<N>_s<L>.map` (4096): `N` - номер уровня (0 - демонстрация, 101-116 люди, 201-216 кунги), `L` - ландшафт 1-4 (файл `w<L>spr.dat`). Карта 64x64 байт, по строкам (`y` сверху вниз), номер тайла;
граница - 0, фон - 1, 120-127 - «хвосты» зданий (смещения к центру `+1, +65, +64, +63, -1, -65, -64, -63` в плоской карте). В `assets_src/maps/NAME.csv` - 64 строки по 64 числа через запятую (открывается в Excel);
**`NAME.png` - просмотр** (1024x1024: настоящие тайлы + герои, свои зелёным, враги красным, пленники синим), для импорта не нужен и создаётся командой `python tools/assets.py preview`.

`map/*.her` (496): записи по 5 байт `{сторона, тип, x, y, extra}`, затем `0xFF` до конца (до 98 героев). Сторона: 0 свои, 1 враги, 2 пленники; тип 0-26 - номер спрайта (по меткам `WW??` в `wlih.asm`:
0 крестьянин (люди), 3 лучник, 4 воин, 5 священник/некромант, 6 волшебник/варлок, 7 катапульта, 8 всадник, 9 пеон, 13 кунг, 17 грюнвер, 18 паук, 19 скелет, 20 скорпион, 21 звезда, 22 князь,
23 Гризольда, 24 костолом, 25 демон, 26 стеногрыз; остальные - не проверялись); `extra` - случайное число из редактора, игре не нужно (сохраняется для точной копии; записывается как число со знаком).
Редактор `WMAPPER2` складывал героев в порядке: свои, враги, пленники, внутри - по строкам карты; импорт порядок не меняет. В `NAME.her.txt` - по строке на героя: `сторона тип x y extra`, комментарии с `;`.

Для 34 уровней 1997 г. параметры и код - в `src/levels/w_???.asm` (читаемый ассемблер), карта, герои, задание и экран - `INCBIN` из `assets/`. **Для 34 дополнительных блоков 1999 г.**
(`reference/cs1999/levels_ext/*.bin`, извлекаются из диска Compu-Studio «New Missions» командой `python tools/extract_cs1999.py`; 33 блока совпадают с `reference/lw2024/.../ExtLev`, `kung_11` у LW испорчен) `tools/levels.py` разбирает блок: `assets_src/levels_ext/<имя>/{script.asm, task.txt, map.csv, heroes.txt, screen.png (+screen.orig.scr), preview.png}`.
`script.asm` - читаемый исходник sjasmplus на первые 1104 байта (`tools/levasm.py`, дизассемблер `tools/disasm.py`): именованные параметры (`hTOWER`, `MONEY`, ... как в `src/levels/w_101.asm`), код задания с `pcLOOP`/`pcINI`/`_cLOOP`,
золото шахт `datMIN`; задание подключается как `INCBIN "task.bin"` (его строит импорт из `task.txt`; хвост старого текста до 63 байт - в комментарии `task.txt`). Сборка `script.asm` даёт точно исходные байты (проверено).
У шести блоков (`human_03, 07, 11`, `kung_03, 09, 13`) в `pcINI` стояла проверка контрольной суммы (TST: сумма `#C000..` или `#4050..` сравнивается с байтом игры `#4002/#400C/#4043/#4045/#7650/#F4AF`; при несовпадении
через ~175 кадров `RST #38`) - `script.asm` у них **очищен** (как в `src/levels/w_104.asm` и др.: `pcINI RET`, `_cLOOP` обычный), а `script.orig.asm` - точная копия LW с защитой (для проверки).
Блоки концовок `*_17e` (старый код чтения диска и экран `w_end_h/k.scr`, полностью совпадающий с нашим) лежат как есть (`NAME.bin`).
Повторный `export` существующие каталоги не трогает (правки `script.asm` не пропадают), `--force` - перезаписать.

## 6. Проверка

`python tools/check_assets.py`: [1] `assets_src` -> импорт -> сверка с `assets/` (226 файлов, побайтно); [2] `assets/` -> экспорт -> импорт -> сверка; [3] каждый файл, который читает сборка (все `INCBIN` в `src/` без `src/original`,
`build.PACKED/FLICKS/MUSIC`), создаётся импортом; [4] цветные экраны без `orig.scr` дают то же изображение; [5] 34 блока доп. уровней: блок -> файлы -> блок. Код возврата 0 - всё совпало.
Расхождений нет. Единственное, что не побайтно **без вспомогательного файла**: `.scr` из PNG без `NAME.orig.scr` (см. 2.1) - это сделано сознательно и оговорено.

## 7. Интеграция в сборку

Статус: **внедрено** (`build.py`: `make_assets()`, `AS = build/assets`; прежний `assets/` перенесён в `archive/assets_raw/`, образы `br1/br2/br_1mb.trd` побайтно совпали с прежними). Ниже - исходное описание:

1. В `build.py` перед `make_data()` добавить шаг «ресурсы из assets_src»:
   ```python
   import assets as assets_tool                       # tools/assets.py (tools уже в sys.path)
   ASRC = os.path.join(ROOT, 'assets_src')
   AS = os.path.join(B, 'assets')                     # было: os.path.join(ROOT, 'assets')

   def make_assets():
       h = hashlib.sha1()
       for base in (ASRC, os.path.join(ROOT, 'tools')):             # изменение исходников или конвертеров
           for d, _, fs in sorted(os.walk(base)):
               for f in sorted(fs):
                   if base == ASRC or f in ('assets.py', 'gfx.py', 'text.py', 'maps.py', 'zxio.py'):
                       h.update(f.encode()); h.update(rd(d, f))
       stamp = os.path.join(AS, '.stamp')
       if os.path.exists(stamp) and open(stamp).read() == h.hexdigest():
           return
       shutil.rmtree(AS, ignore_errors=True)
       assets_tool.do_import(ASRC, AS)               # ~4 с; при ошибке в тексте/картинке исключение называет файл и строку
       open(stamp, 'w').write(h.hexdigest())
   ```
   и вызвать `make_assets()` первой строкой `main()`.
2. Больше ничего менять не нужно: `asm()` уже передаёт `-I AS`, а `INCBIN "data/..."`, `"map/..."`, `"task/..."`, `"barkov/..."` в `src/` и все `rd(AS, ...)` в `build.py` используют те же относительные пути -
   `import` пишет каталог с тем же составом и именами, что `assets/` (проверено п. [1] и [3]). Кэш упаковки `build/cache` ключуется содержимым, поэтому после перехода ничего не перепаковывается.
3. Порядок внедрения: (а) после регресс-теста запустить `python tools/check_assets.py` (должно быть `ВСЁ СОВПАДАЕТ`), (б) внести правку, собрать, убедиться, что `br1.trd`, `br2.trd`, `br_1mb.trd` побайтно совпадают с прежними (сверка хэшей),
   (в) оставить `assets/` как эталон только для `check_assets.py` или перенести в `archive/`; после этого править ресурсы можно только в `assets_src/`.
4. Дополнительные уровни: `python tools/levels.py import --out build/levels_ext` даёт 34 блока `human_NN.bin`/`kung_NN.bin` (после правок параметров/карт/текстов). Удаление проверок контрольных сумм (`TST`) и замена `*_17e` -
   отдельная задача (см. `docs/NOTES.md`): правится `script.bin`, либо блок дизассемблируется в `src/levels`.
5. Рабочий цикл переводчика/художника: правит PNG/`.txt`/CSV -> `python build.py` (импорт срабатывает сам) -> для проверки `python tools/check_assets.py` (после правок п. [1] покажет отличия от `assets/`, это нормально
   и означает «ресурс изменён»; после внедрения проверку можно перевести на сравнение с `assets/` только по флагу).
